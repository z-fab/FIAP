Capítulo 04

Empacotamento e Tooling Profissional

Configurar o projeto como um pacote reutilizável com automação de qualidade (uv, ruff, taskipy, Makefile) e uma estratégia clara para versionar modelo e API juntos.

Introdução

Até aqui, o projeto California Housing provavelmente vive como um conjunto de notebooks e arquivos .py soltos, com dependências instaladas "na fé" via pip install direto no ambiente global. Isso funciona para explorar dados, mas desmorona no momento em que outra pessoa (ou o seu eu de daqui a três meses) tenta rodar o código. As versões das bibliotecas não batem, o import quebra com ModuleNotFoundError, e ninguém sabe qual modelo foi treinado com qual commit.

Engenharia de software resolve esses problemas com três pilares que vamos montar agora:

  1. Reprodutibilidade — qualquer pessoa instala e roda o projeto com um comando, obtendo exatamente as mesmas versões de dependências (via uv e uv.lock).
  2. Qualidade automatizada — lint, formatação e testes rodam com um comando curto (ruff, taskipy, Makefile).
  3. Rastreabilidade de versão — o artefato pipeline.joblib e a API que o serve evoluem em conjunto, com versão e hash explícitos.

O objetivo final é que from housing import ... funcione em qualquer máquina, e que comandos como task lint, task test, task train e task run sejam o cotidiano do projeto.

🎯

Sem a seção [build-system], from housing import ... falha com ModuleNotFoundError — é a causa nº 1 do "instalei tudo e não importa".

📖 Definição

Pacote vs. script. Um script é um arquivo .py que você executa diretamente. Um pacote é uma coleção de módulos organizada e instalável, que pode ser importada de qualquer lugar do ambiente (import housing). A diferença prática: um script só funciona se você estiver na pasta certa; um pacote instalado funciona em qualquer diretório, em testes, e quando empacotado num container.

Quando virar pacote — e onde entra o Dockerfile

Uma dúvida comum: "se eu já vou colocar tudo num container, ainda preciso transformar o projeto num pacote instalável?". A resposta é sim, porque pacote e Dockerfile resolvem problemas diferentes e são complementares, não alternativas. Um não substitui o outro; na prática, os dois costumam andar juntos.

O pacote instalável resolve o "meu código importa em qualquer lugar": ele torna o seu código uma biblioteca importável e reutilizável, de modo que a API, os testes e os scripts de treino façam todos import housing sem depender de qual pasta você está. Já o Dockerfile resolve o "roda igual em qualquer lugar": ele empacota a aplicação junto com o ambiente (sistema operacional, versão do Python, dependências) para rodar e deployar de forma reprodutível em qualquer máquina ou servidor.

Na prática você costuma ter os dois: o Dockerfile instala o seu pacote dentro da imagem. A regra de bolso:

✓ Faça um pacote
  • Quando o código for importado por outros módulos.
  • Quando o código for reutilizado entre API, testes e treino.
  • Quando precisar compartilhar a lógica entre partes do projeto.
✓ Faça um Dockerfile
  • Quando precisar empacotar a aplicação com o ambiente.
  • Quando precisar deployar para rodar fora da sua máquina.
  • Por dentro, ele instala o seu pacote — os dois andam juntos.
pacoteCódigo importável

Transforma o projeto numa biblioteca: import housing funciona em qualquer lugar. Resolve a reutilização do código — API, testes e treino compartilham os mesmos módulos.

DockerfileAmbiente reprodutível

Empacota a aplicação com o ambiente (SO, Python, deps) para rodar igual em qualquer máquina. Resolve o deploy reprodutível — e por dentro ele instala o seu pacote.

1. uv: o gerenciador de ambiente e projeto

O uv é uma ferramenta da Astral, escrita em Rust e lançada em fevereiro de 2024. Ele substitui, num único binário, todo um zoológico de ferramentas que cientistas de dados costumam misturar: pip, pip-tools, virtualenv, poetry, pyenv e pipx. Além de unificar, ele é absurdamente rápido: de 8 a 10x mais rápido que o pip sem cache, e de 80 a 115x com cache quente.

900+
regras de lint no ruff (substitui flake8, isort, black...)

1.1 A decisão crítica: uv init --package

Existem dois jeitos de iniciar um projeto:

  • uv init (sem flag) — cria apenas um hello.py na raiz. Não cria pasta src/, não cria [build-system], e portanto o seu código não vira um pacote importável.
  • uv init --package nome — cria a estrutura de pacote completa, com src/nome/__init__.py e o [build-system] no pyproject.toml.

Como queremos from housing import ..., usamos sempre a segunda forma:

uv init --package housing

Estrutura gerada:

housing/
├── pyproject.toml        # com [build-system] E [project]
├── README.md
├── .python-version
├── uv.lock               # criado/atualizado a cada uv add/sync
└── src/
    └── housing/
        └── __init__.py
⚠️ Atenção

A diferença que quebra tudo. Se você rodar uv init (sem --package), o pyproject.toml sai sem a seção [build-system]. Sem ela, o uv sync não instala o seu projeto no ambiente, e qualquer from housing import x falha com ModuleNotFoundError. Esta é a causa mais comum de "mas eu instalei tudo e não importa!". Sempre verifique se há um bloco [build-system].

1.2 Adicionando dependências

Em vez de pip install, usamos uv add. Cada uv add atualiza o pyproject.toml e o uv.lock, e instala no ambiente virtual do projeto.

# Dependências de runtime (a API e o pipeline precisam delas em produção)
uv add fastapi uvicorn 'scikit-learn>=1.4' polars pydantic joblib

# Dependências de desenvolvimento (NÃO vão para a distribuição)
uv add --dev pytest ruff taskipy pandera

Comandos do dia a dia:

uv sync                            # cria o venv e instala tudo (modo editável)
uv run python -m housing.modeling.train     # roda algo dentro do venv, sem ativá-lo
uv run pytest                      # roda os testes
uv lock --upgrade-package fastapi  # atualiza só uma dependência no lock
uv add -r requirements.txt         # importa um projeto legado
uv sync --frozen                   # CI/Docker: usa o lock exato, não recalcula
📖 Definição

uv.lock. Arquivo TOML legível, gerado e mantido pelo uv. Registra as versões exatas de todas as dependências (diretas e transitivas), de forma reprodutível e cross-platform. Nunca edite à mão — só via comandos uv. Comite-o no Git: é o que garante que todo mundo instale exatamente as mesmas versões.

💡 Dica

Modo editável é automático. Quando há [build-system], o uv sync e o uv run instalam o seu pacote em modo editável por padrão. Você edita o código em src/housing/ e a mudança vale na hora, sem reinstalar.

2. pyproject.toml: o coração do projeto (PEP 621)

O pyproject.toml é o arquivo único de configuração de projetos Python modernos (PEP 621). Substitui o antigo trio setup.py / setup.cfg / requirements.txt e centraliza: metadados, dependências, como construir o pacote, scripts executáveis e a configuração de ferramentas como ruff e taskipy.

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "housing"
version = "0.1.0"
description = "API de inferência de preços de imóveis na Califórnia"
readme = "README.md"
requires-python = ">=3.11"
license = { text = "MIT" }
authors = [{ name = "Equipe Data Science", email = "ds@exemplo.com" }]
dependencies = [
    "fastapi",
    "uvicorn",
    "scikit-learn>=1.4",
    "polars",
    "pydantic",
    "joblib",
]

[dependency-groups]
dev = ["pytest", "ruff", "taskipy", "pandera"]

[project.scripts]
housing-api = "housing.api.entry:run"

[tool.ruff]
line-length = 88
target-version = "py311"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]

[tool.ruff.format]
quote-style = "double"

[tool.taskipy.tasks]
lint = "ruff check . && ruff format --check ."
format = "ruff check --fix . && ruff format ."
test = "pytest tests/ -v"
train = "python -m housing.modeling.train"
run = "uvicorn housing.api.app:app --reload"

2.1 Entendendo as seções

  • [build-system] — diz ao Python como construir o pacote. Usamos hatchling. Sem esta seção, seu pacote não é instalável.
  • [project] — os metadados. O name pode ter hífen, mas o módulo importável usa underscore.
  • dependencies — o que o projeto precisa em runtime.
  • [dependency-groups] (PEP 735, uv ≥ 0.4) — dependências locais de desenvolvimento que não vão para a distribuição. Instala com uv sync --group dev.
  • [project.scripts] — entry points. housing-api = "housing.api.entry:run" cria um comando de terminal housing-api.
💡 Dica

[dependency-groups] vs. [project.optional-dependencies]. As optional-dependencies (instaladas com uv sync --extra dev) vão para a distribuição publicada — útil para extras ao usuário final (pip install housing[train]). Já os dependency-groups (uv sync --group dev) são puramente locais. Para ferramentas de dev (pytest, ruff), use dependency-groups.

2.2 src layout: por que src/?

O src layout coloca o código em src/housing/ em vez de housing/ na raiz. A vantagem é decisiva: o pacote só é importável depois de instalado. Isso garante que seus testes rodem contra a versão instalada (como o usuário verá), e não acidentalmente contra os arquivos soltos do diretório atual.

2.3 Guia das seções

Cada seção do pyproject.toml acima tem um papel bem definido. O guia abaixo resume o que cada uma faz:

SeçãoO que faz
[build-system]Define o backend de build (hatchling). Sem ela, o uv sync não instala o pacote e import housing falha com ModuleNotFoundError.
[project]Metadados do pacote: nome, versão, descrição, Python mínimo, autores e licença — o que vai para a distribuição.
dependenciesBibliotecas de runtime (fastapi, uvicorn, scikit-learn, polars, pydantic, joblib) — o que a API e o pipeline precisam em produção.
[dependency-groups]Dependências locais de desenvolvimento (pytest, ruff, taskipy, pandera). PEP 735; instala com uv sync --group dev e não vão para a distribuição.
[project.scripts]Entry points: comandos de terminal instalados com o pacote (housing-api → função housing.api.entry:run). Diferente do taskipy, que é só automação de dev.
[tool.ruff] · .lint · .formatConfiguração do linter/formatter. As regras de lint (select) ficam em [tool.ruff.lint]; a formatação em [tool.ruff.format]; a config geral (line-length) em [tool.ruff].
[tool.taskipy.tasks]Atalhos de desenvolvimento (task lint, task test, task run…). Rodam comandos de shell e não vão para a distribuição.

3. ruff: lint e format num só binário

O ruff, também da Astral, é um linter e formatter escrito em Rust, com mais de 900 regras. Sozinho substitui flake8, pylint, isort, black, pydocstyle e pyupgrade. Mas antes do código, vale fixar os dois conceitos que ele combina:

linterAponta problemas

Um linter analisa o código sem executá-lo e aponta problemas: imports não usados, variáveis não definidas, bugs prováveis, violações de estilo. Ele não muda nada — só te avisa.

formatterReescreve o estilo

Um formatter reescreve o código automaticamente num estilo consistente (espaçamento, aspas, quebras de linha), sem alterar o comportamento. Tira a discussão de estilo da revisão de código.

O ruff faz os dois, num único binário e muito rápido. São dois subcomandos distintos — confundi-los é um erro comum:

ruff check .            # LINT: encontra problemas (imports não usados, bugs, etc.)
ruff check --fix .      # LINT + corrige automaticamente o que dá
ruff format .           # FORMAT: reformata o código (equivalente ao black)
ruff format --check .   # FORMAT em modo verificação (não altera) — para CI
⚠️ Atenção

select vai dentro de [tool.ruff.lint]. Em versões recentes do ruff, as regras de lint (select, ignore) ficam em [tool.ruff.lint], não em [tool.ruff]. A configuração geral (line-length, target-version) fica em [tool.ruff]; o lint em [tool.ruff.lint]; a formatação em [tool.ruff.format].

No nosso pyproject.toml, select = ["E", "F", "I", "UP", "B", "SIM"] ativa: erros de estilo (E), Pyflakes (F), ordenação de imports (I, equivale ao isort), modernização de sintaxe (UP), bugs prováveis (B, bugbear) e simplificações (SIM).

4. taskipy: atalhos no próprio pyproject

Digitar uvicorn housing.api.app:app --reload toda vez é tedioso. O taskipy define atalhos diretamente no pyproject.toml, em [tool.taskipy.tasks]. Para usar:

task lint      # ruff check . && ruff format --check .
task format    # ruff check --fix . && ruff format .
task test      # pytest tests/ -v
task train     # python -m housing.modeling.train
task run       # uvicorn housing.api.app:app --reload
task --list    # lista todas as tasks disponíveis
⚠️ Atenção

task precisa do venv. O comando task só funciona com o ambiente virtual ativado, ou prefixado com uv run task lint. Como não ativamos venvs manualmente neste fluxo, prefira sempre uv run task <nome>.

4.1 [project.scripts] vs. taskipy

Os dois geram "comandos", mas servem a públicos opostos — e é fácil confundi-los:

[project.scripts]Comandos do pacote

Entry points instalados com o pacote: ficam disponíveis para quem instala o pacote e apontam para uma função Python (housing-api → housing.api.entry:run). São parte da distribuição/produto.

taskipyAutomação de dev

Atalhos de desenvolvimento (lint/test/run) que rodam comandos de shell e não vão para a distribuição. Servem ao fluxo do dev, não ao usuário final do pacote.

🎯

Em resumo: [project.scripts] = comandos públicos do pacote (vão para quem instala); taskipy = automação interna de tarefas (fica no seu fluxo de dev).

O taskipy suporta hooks (pre_test, post_train) e tasks com descrição:

[tool.taskipy.tasks]
lint = { cmd = "ruff check . && ruff format --check .", help = "Verifica lint e formatação" }
⚠️ Atenção

Cuidado com loops em hooks. Um hook pre_lint = "task lint" chama task lint, que dispara pre_lint de novo, criando recursão infinita. Hooks devem chamar comandos diferentes da própria task.

5. Makefile: o bootstrap universal

Se o taskipy já dá atalhos, por que um Makefile? Porque o make não depende de Python nem de venv ativado. Ele é a porta de entrada universal: alguém que clonou o repositório e ainda não tem nada instalado pode rodar make install. Os demais alvos delegam para uv run.

.PHONY: install lint format test train run clean

install:
	uv sync --group dev

lint:
	uv run task lint

format:
	uv run task format

test:
	uv run task test

train:
	uv run task train

run:
	uv run task run

clean:
	rm -rf .pytest_cache .ruff_cache **/__pycache__
⚠️ Atenção

.PHONY é essencial. Sem a declaração .PHONY, o make pensa que test, clean etc. são arquivos a serem construídos. Se existir um arquivo ou pasta chamado test, o make test simplesmente não roda nada. .PHONY diz ao make que esses alvos são comandos. (Lembre: indentação de Makefile usa TAB, não espaços.)

🎯

São três camadas que se delegam: make → task → uv run → ferramenta real (ruff, pytest, uvicorn). Cada uma existe para um público.

make
Bootstrap universal

Para quem chega de fora: não depende de Python nem de venv ativado.

task
Atalhos de projeto

Para quem já está no projeto: comandos curtos definidos no pyproject.toml.

uv run
Garante o ambiente

Executa no venv correto, sem precisar ativá-lo, e delega para a ferramenta real.

6. Versionamento de modelos

A API e o modelo são dois artefatos que evoluem juntos, e desincronizá-los causa bugs sutis. Você atualiza a API esperando um modelo novo, mas o pipeline.joblib ainda é o antigo — isso é o drift de versão, e ele falha em silêncio (sem erro, só previsões erradas).

6.1 Por que versionar modelos

Versionar não é burocracia: é o que torna o sistema de ML auditável e recuperável. Quatro motivos concretos:

  • Reprodutibilidade — conseguir recriar exatamente a previsão que um modelo deu numa certa data, com os mesmos dados e código.
  • Rollback — se um modelo novo piorar em produção, voltar para a última versão boa em minutos, não em dias.
  • Auditoria — saber quem treinou o quê, com quais dados e parâmetros — essencial em domínios regulados.
  • Compatibilidade modelo↔API — garantir que a versão do modelo carregada bate com o contrato de entrada/saída que a API espera.

6.2 O que versionar (não é só o .joblib)

Versionar "o modelo" de verdade significa amarrar quatro coisas, não apenas o arquivo de pesos:

artefatoO modelo treinado

O pipeline.joblib — pré-processamento + estimador serializados. É o que a API carrega para servir previsões.

códigoComo foi feito

O código de treino e da API, versionado no Git (commit/tag). Define a lógica de feature engineering e o contrato da API.

dadosCom o que treinou

Os dados de treino (ou seu fingerprint/hash). Mesmo código + dados diferentes geram modelos diferentes.

metadadosO contexto

Métricas, params, hash dos dados e versão do sklearn — o meta.json do capítulo 1. É o que torna o modelo auditável.

6.3 Semver para modelos

Adaptamos o Semantic Versioning (MAJOR.MINOR.PATCH) ao ciclo de vida do modelo:

MAJOR
Quebra de contrato

Nova arquitetura ou mudança que quebra o contrato: features de entrada diferentes ou formato de saída novo.

MINOR
Retreino compatível

Retreino com a mesma arquitetura: novos dados, mas mesmas features e mesma saída.

PATCH
Ajuste fino

Ajuste de threshold ou correção de bug no pré-processamento, sem mudar o comportamento esperado.

6.4 Boas práticas

  • Artefatos são imutáveis — nunca sobrescreva um pipeline.joblib existente. Versione no nome ou no registry; sobrescrever apaga a possibilidade de rollback e auditoria.
  • Registre o fingerprint dos dados — um hash do conjunto de treino, gravado nos metadados, prova com qual recorte de dados aquele modelo nasceu.
  • Amarre modelo + código + dados por um commit/tag de Git, para que git checkout <tag> restaure o trio exato.
  • Automatize a promoção — a passagem de staging → produção deve ser um passo deliberado e registrado, não um arquivo copiado na mão.

6.5 Lock explícito no código

A documentação não basta — a versão precisa estar travada no código:

# src/housing/version.py
MODEL_VERSION = "2.3.1"
MODEL_URI = f"models:/california-housing/{MODEL_VERSION}"

E uma tag de Git conjunta amarra o commit do código da API à referência do artefato. Mantenha também um CHANGELOG e, idealmente, uma matriz de compatibilidade API × modelo.

6.6 Na prática: MLflow e DVC

Na prática, ferramentas dedicadas tiram esse trabalho das suas costas. Com o MLflow, você registra o modelo versionado no treino e carrega uma versão específica ao servir:

import mlflow

# ao treinar: registra o modelo versionado
mlflow.sklearn.log_model(pipeline, name="model", registered_model_name="california-housing")

# ao servir: carrega uma versão específica
model = mlflow.sklearn.load_model("models:/california-housing/3")

Para os dados e artefatos pesados, que não cabem no Git, entra o DVC: ele os versiona fora do Git, deixando no repositório só um ponteiro leve.

📖 Definição

MLflow Model Registry e DVC. O MLflow Model Registry organiza modelos em estágios — Staging → Production → Archived — e captura, junto, o commit do Git, parâmetros, métricas e artefato. Atenção: esses estágios são lógicos, não ambientes físicos; marcar como "Production" não faz deploy. O DVC versiona dados e modelos pesados fora do Git: um arquivo .dvc pequeno fica no Git apontando para o S3/GCS, e git checkout <tag> + dvc pull restaura o par exato código+modelo. Armadilha: se o remote não estiver configurado, o dvc pull falha de forma silenciosa.

7. Construir sua própria API ou usar serving pronto?

Para servir o pipeline.joblib, há duas abordagens de fundo. Você pode construir a sua própria API (com FastAPI ou Flask) ou usar uma solução pronta de serving (BentoML, MLflow Models serve, Triton...). A escolha depende menos de moda e mais do estágio do projeto, da escala e do hardware.

42%
dos engenheiros de ML usam FastAPI para servir modelos (2025)

De um lado, construir a sua própria significa escrever a API você mesmo: controle total, poucas dependências, simples de entender. É ótimo para casos simples ou customizados, para aprender, ou para embutir o ML dentro de uma aplicação maior. Do outro lado, usar serving pronto traz empacotamento, versionamento, batching e escalabilidade "de fábrica" — menos código seu, mas mais um framework para aprender e adotar.

Construir a sua própria vs. usar serving pronto

Para o California Housing — um modelo único, em CPU, servindo previsões REST — FastAPI próprio é suficiente: pouca dependência, total controle e fácil de entender. As soluções prontas de serving brilham quando o cenário cresce — escala alta, múltiplos modelos ou GPU — e o empacotamento/versionamento embutido passa a compensar a curva de aprendizado.

🎯

Regra de decisão: construa a sua própria API quando o caso é simples ou o ML é embutido numa app maior; use serving pronto quando há escala, muitos modelos ou GPU em jogo.

Todo esse tooling precisa estar documentado no README.md do projeto, para que a próxima pessoa (ou o avaliador) saiba como começar:
