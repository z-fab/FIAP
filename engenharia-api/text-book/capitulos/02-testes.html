Capítulo 02

Testes Automatizados em ML

Escrever uma suíte de testes que dá confiança no pipeline de ML usando pytest, pandera e smoke tests.

Introdução: o pesadelo silencioso

Em um notebook Jupyter, quando algo dá errado, você normalmente vê. Uma célula lança KeyError, o traceback fica vermelho e você sabe exatamente onde parar. O problema é que a classe de bugs mais perigosa em ML não lança exceção nenhuma.

Imagine que o time de dados, lá no sistema que alimenta o seu modelo, renomeia a coluna median_income para median_household_income. Seu código de pré-processamento, que esperava median_income, não encontra a coluna, gera NaN em uma feature derivada, o modelo prediz números plausíveis (só que errados), a API responde 200 OK, e ninguém percebe — até alguém auditar os resultados meses depois.

Um sistema de ML pode rodar até o fim sem lançar nenhuma exceção e mesmo assim produzir resultados completamente errados.

É justamente por isso que testar código de ML não é "burocracia de engenheiro": é o mecanismo que transforma falhas silenciosas em falhas barulhentas, que aparecem na sua máquina antes de chegarem em produção.

📖 Definição

Falha silenciosa (silent failure): quando o programa roda até o fim sem erro, mas produz um resultado incorreto. Em ML é a regra, não a exceção — dados são uma entrada que muda sozinha ao longo do tempo, fora do seu controle.

O que quebra silenciosamente em ML

  • Data leakage: informação do alvo "vaza" para as features. O modelo parece ótimo no papel e fracassa no mundo real.
  • Schema drift upstream: uma coluna muda de nome, de tipo (int → string) ou some. Resultado: NaN silencioso ou erro de tipo mascarado.
  • Features dropadas: uma etapa de seleção remove uma coluna sem ninguém notar.
  • Pré-processamento inconsistente treino/serviço: você normaliza de um jeito no treino e de outro na API.
  • Data drift / concept drift: a distribuição dos dados de entrada (ou a relação entre features e alvo) muda com o tempo.
🎯

O fio comum: ML falha sem lançar exceção. O código roda, a API responde 200 OK — e o resultado está errado. Testar é transformar essa falha silenciosa em uma falha barulhenta.

Cada um desses modos tem um tipo de teste que o pega melhor. É disso que trata a pirâmide a seguir.

A pirâmide de testes, adaptada para ML

A pirâmide de testes é uma ideia consagrada em engenharia de software: muitos testes rápidos e baratos na base, poucos testes lentos e caros no topo. A intuição: testes de unidade são tão baratos que você roda centenas a cada salvar; testes de ponta a ponta são caros, então você tem só um punhado.

Para ML, adaptamos as três camadas assim:

Mas o que é, na prática, cada uma dessas camadas? Antes de descer ao código, vale fixar os três tipos de teste que vamos usar:

unitTeste unitário

Verifica uma peça isolada do código — uma função ou um transformador — com entradas pequenas e conhecidas. Ex.: "dado este DataFrame, a coluna derivada tem o valor que calculei na mão?". São rápidos e numerosos.

schemaTeste de schema

Não testa o código, e sim os dados: confere que cada coluna existe, tem o tipo certo e cai em valores plausíveis (ex.: latitude entre 32 e 42). Pega dados corrompidos ou que mudaram de formato antes de chegarem ao modelo.

smokeSmoke test

Teste de sanidade do sistema inteiro: o pipeline carrega, treina sem estourar e devolve uma previsão com o formato esperado. Não mede qualidade — só responde "está vivo?".

A ordem da pirâmide reflete uma heurística simples: tenha muitos testes unitários e de schema (baratos e estáveis) e poucos testes mais amplos. A razão está em como cada tipo envelhece:

  • Testes de unidade são aditivos: um dado novo entrando no sistema não invalida um teste de unidade existente.
  • Testes de integração são retroativos: dependem do estado atual do sistema e podem precisar ser revistos quando o ambiente muda.

Por isso a base é unit: ela é estável e barata. Vamos construir a pirâmide de baixo para cima.

pytest: o básico que você precisa saber

Se você vem do Jupyter, a transição mental é simples: um teste é só uma função que prepara dados, roda seu código e verifica o resultado. Esse padrão tem nome — Arrange-Act-Assert (AAA) — e é a espinha dorsal de todo bom teste.

Diagrama · Anatomia de um teste (Arrange → Act → Assert)
1 · Arrange — preparar
df = pl.DataFrame({"total_rooms": [6.0], "households": [2.0]})

monto a entrada mínima e conhecida

↓
2 · Act — executar
out = AddRoomsPerHousehold().transform(df)

rodo exatamente o que quero testar

↓
3 · Assert — verificar
assert out["rooms_per_household"][0] == pytest.approx(3.0)

confiro o resultado contra o esperado

Fixtures: dados de teste reutilizáveis

No notebook você cria um df de exemplo e reaproveita em várias células. Em pytest, o equivalente é uma fixture: uma função decorada com @pytest.fixture cujo retorno é injetado em qualquer teste que a peça por nome no argumento.

import pytest
import polars as pl

@pytest.fixture
def amostra_housing():
    """DataFrame mínimo no schema do California Housing."""
    return pl.DataFrame({
        "MedInc":     [8.32, 5.64],
        "HouseAge":   [41.0, 21.0],
        "AveRooms":   [6.98, 6.24],
        "AveBedrms":  [1.02, 0.97],
        "Population": [322.0, 2401.0],
        "AveOccup":   [2.55, 2.11],
        "Latitude":   [37.88, 37.86],
        "Longitude":  [-122.23, -122.22],
    })
📖 Definição

conftest.py: arquivo especial do pytest onde você coloca fixtures compartilhadas por vários arquivos de teste — sem precisar importá-las. Toda fixture definida ali fica disponível automaticamente para os testes na mesma pasta (e subpastas). É o conceito que mais confunde quem vem de Jupyter: não há import, o pytest injeta por nome.

Escopo: com que frequência a fixture é recriada

Toda fixture tem um escopo, que decide quantas vezes ela é executada. O padrão recria a fixture a cada teste (isolamento máximo); escopos mais amplos economizam tempo quando o preparo é caro. Declara-se no decorador: @pytest.fixture(scope="session").

functionpadrão

Recriada a cada teste. Cada teste recebe um objeto novo e limpo — sem risco de um teste contaminar o outro.

modulepor arquivo

Criada uma vez por arquivo de teste e compartilhada por todos os testes dele.

sessionuma vez só

Criada uma única vez para toda a execução. Ideal para algo caro, como treinar um modelo de brinquedo reaproveitado por vários testes.

Setup e teardown com yield

Às vezes a fixture precisa limpar algo depois do teste — fechar uma conexão, remover um arquivo temporário. Para isso, troque o return por yield. A regra é simples: tudo antes do yield é o setup (roda antes do teste); o valor entregue no yield é injetado no teste; tudo depois do yield é o teardown (roda quando o teste termina, mesmo se ele falhar).

@pytest.fixture
def modelo_treinado(amostra_housing):
    modelo = treinar(amostra_housing)   # setup: roda antes do teste
    yield modelo                        # valor injetado no teste
    modelo.fechar_recursos()            # teardown: roda depois do teste

Para arquivos temporários, o pytest já oferece a fixture embutida tmp_path (um diretório limpo por teste, apagado automaticamente depois) — ideal para testar save()/load() do modelo sem sujar o disco.

Parametrização: muitos casos, um teste

Em vez de copiar o mesmo teste várias vezes mudando só os números, o @pytest.mark.parametrize roda a mesma função uma vez para cada linha de uma tabela de casos. O primeiro argumento nomeia os parâmetros (separados por vírgula); cada tupla seguinte vira uma execução independente — e aparece separada no relatório, então você sabe exatamente qual caso falhou. É a forma mais econômica de cobrir vários cenários, inclusive os casos-limite.

@pytest.mark.parametrize("total_rooms,households,esperado", [
    (6.0, 2.0, 3.0),
    (10.0, 5.0, 2.0),
    (0.0, 1.0, 0.0),
])
def test_rooms_per_household(total_rooms, households, esperado):
    df = pl.DataFrame({"total_rooms": [total_rooms], "households": [households]})
    out = AddRoomsPerHousehold().transform(df)
    assert out["rooms_per_household"][0] == pytest.approx(esperado)
💡 Dica

Ponto de entrada mais fácil para quem vem de Jupyter: comece testando suas funções puras de feature engineering com parametrize. São funções sem estado, e cada linha da tabela é um caso que você já checaria "no olho" em uma célula. Empilhar dois @parametrize gera o produto cartesiano dos casos.

E o pytest.approx? Comparar floats com == é furada (0.1 + 0.2 != 0.3). pytest.approx compara com tolerância — use sempre que o resultado for número de ponto flutuante.

Camada 1 — Teste unitário do transformador

Vamos testar o transformador que criamos no capítulo anterior — aquele que adiciona uma feature derivada (cômodos por domicílio). Antes, um lembrete do que é um transformador e por que ele tem uma etapa de "treino".

📖 Definição

Transformador é um objeto com dois métodos: fit, que aprende dos dados o que precisar, e transform, que aplica a transformação. Por que "aprender"? Porque muitos pré-processamentos dependem de estatísticas do conjunto de treino: o StandardScaler calcula a média e o desvio no fit para depois usá-los no transform; um codificador de categorias precisa primeiro descobrir quais categorias existem. Treinar o transformador é exatamente esse passo de medir os parâmetros — e ele só pode olhar os dados de treino, senão reabre o data leakage do capítulo 1.

O nosso transformador é mais simples: a conta é fixa (uma divisão), então não há nada a aprender e o fit apenas devolve self. Ainda assim ele segue o contrato fit/transform, para poder entrar num pipeline:

# src/modeling/transformers.py
import polars as pl
from sklearn.base import BaseEstimator, TransformerMixin

class AddRoomsPerHousehold(BaseEstimator, TransformerMixin):
    """Adiciona a feature rooms_per_household = total_rooms / households."""

    def fit(self, X, y=None):
        return self  # transformador sem estado (nada a aprender)

    def transform(self, X: pl.DataFrame) -> pl.DataFrame:
        return X.with_columns(
            (pl.col("total_rooms") / pl.col("households"))
            .alias("rooms_per_household")
        )

Um bom teste unitário de transformer cobre três coisas: shape do output, valores corretos e conformidade com a API do sklearn.

# tests/test_transformers.py
import polars as pl
import pytest
from sklearn.base import clone
from src.modeling.transformers import AddRoomsPerHousehold

@pytest.fixture
def df_base():
    return pl.DataFrame({"total_rooms": [6.0, 10.0], "households": [2.0, 5.0]})

def test_adiciona_uma_coluna(df_base):
    out = AddRoomsPerHousehold().transform(df_base)   # Act
    assert out.shape == (2, 3)                         # +1 coluna
    assert "rooms_per_household" in out.columns

def test_valores_corretos(df_base):
    out = AddRoomsPerHousehold().transform(df_base)
    assert out["rooms_per_household"].to_list() == pytest.approx([3.0, 2.0])

def test_clone_preserva_params():
    # GridSearchCV depende de clone(): get_params/set_params bem comportados
    t = AddRoomsPerHousehold()
    assert t.get_params() == clone(t).get_params()

Para verificar o contrato da API do sklearn (essencial dentro de Pipeline/GridSearchCV):

from sklearn.utils.estimator_checks import parametrize_with_checks
from src.modeling.transformers import AddRoomsPerHousehold

@parametrize_with_checks([AddRoomsPerHousehold()])
def test_conformidade_sklearn(estimator, check):
    check(estimator)

parametrize_with_checks (sklearn ≥ 1.1) roda dezenas de verificações de conformidade automaticamente.

⚠️ Atenção

Os checks automáticos do sklearn geram dados sintéticos em NumPy. Se o seu transformador aceita só um tipo específico de entrada (por exemplo, apenas DataFrames), esse teste pode falhar — o que é informação útil: ou você o torna mais flexível, ou cobre a conformidade com os testes manuais que já escrevemos (shape, clone, get_params).

Camada 2 — Validação de schema com pandera

Testes unitários cuidam do seu código. Mas e os dados que entram? Eles vêm de fora, mudam sozinhos e são a maior fonte de falhas silenciosas. A camada do meio é um portão de dados: nada passa para o pipeline sem antes ser validado.

O pandera é uma biblioteca para declarar e validar o "contrato" de um DataFrame. Você descreve como os dados deveriam ser — colunas, tipos, faixas de valores — e o pandera confere se um DataFrame cumpre esse contrato, levantando um erro claro quando não cumpre.

Ele nasceu para o pandas (import pandera as pa), que continua sendo o caminho mais completo. Também há suporte a Polars (import pandera.polars as pa) — é o que usamos aqui —, com a mesma ideia e praticamente a mesma API.

pip install pandera            # para pandas
pip install 'pandera[polars]'  # com suporte a Polars
📖 Definição

Schema: o contrato dos seus dados — quais colunas existem, de que tipo são, e que valores são aceitáveis. Validar o schema é checar que os dados que chegaram cumprem esse contrato antes de qualquer processamento.

Dois jeitos de declarar um schema

O pandera oferece dois estilos — equivalentes no resultado, diferentes na forma de escrever:

DataFrameSchema · imperativo

Você monta um objeto passando um dicionário de colunas: pa.DataFrameSchema({"MedInc": pa.Column(float, pa.Check.gt(0))}). Útil quando o schema é gerado dinamicamente, em tempo de execução.

DataFrameModel · declarativo

Você escreve uma classe com as colunas como atributos tipados. É o que vamos usar: lê-se como documentação, aproveita os type hints e o autocompletar do editor.

Em formato de classe (DataFrameModel), o contrato do nosso dataset fica assim:

# src/data/schema.py
import pandera.polars as pa
from pandera.typing.polars import Series

class HousingSchema(pa.DataFrameModel):
    MedInc:     Series[float] = pa.Field(gt=0.0)
    HouseAge:   Series[float] = pa.Field(in_range={"min_value": 0.0, "max_value": 100.0})
    AveRooms:   Series[float] = pa.Field(gt=0.0)
    AveBedrms:  Series[float] = pa.Field(gt=0.0)
    Population: Series[float] = pa.Field(gt=0.0)
    AveOccup:   Series[float] = pa.Field(gt=0.0)
    Latitude:   Series[float] = pa.Field(in_range={"min_value": 32.0, "max_value": 42.0})
    Longitude:  Series[float] = pa.Field(in_range={"min_value": -125.0, "max_value": -114.0})

    class Config:
        coerce = True   # tenta converter os tipos automaticamente

O que cada restrição do Field significa

Cada coluna pode declarar regras dentro do Field. As mais usadas:

RestriçãoO que exige
gt / gemaior que / maior ou igual a (greater than / greater or equal)
lt / lemenor que / menor ou igual a (less than / less or equal)
in_rangedentro de um intervalo {"min_value":…, "max_value":…}
isinpertence a uma lista de valores permitidos — ideal para categorias
str_lengthcomprimento do texto dentro de limites
nullablepermite valores nulos (por padrão, não permite)
uniqueexige valores únicos na coluna (ex.: um id)
coercetenta converter o tipo automaticamente (ex.: texto "41" → número)

Validar é uma linha — validate devolve o próprio DataFrame se estiver tudo certo, ou levanta um erro descrevendo a primeira violação:

import polars as pl
from src.data.schema import HousingSchema

df = pl.read_csv("housing.csv")
HousingSchema.validate(df)   # levanta SchemaError se algo estiver fora do contrato

Por padrão a validação para no primeiro erro. Para coletar todos de uma vez (ótimo ao depurar um dataset novo), use lazy=True:

import pandera.errors as pa_errors

try:
    HousingSchema.validate(df, lazy=True)
except pa_errors.SchemaErrors as exc:
    print(exc.failure_cases)   # tabela com TODAS as violações
⚠️ Atenção

Permitir nulos é explícito. Por padrão, uma coluna não aceita valores nulos. Se a sua pode ser nula, diga claramente — e não confie só em anotar o tipo como opcional: declare pa.Field(ge=0.0, nullable=True). Esquecer o nullable=True é uma fonte comum de validações que passam (ou falham) quando não deveriam.

⚠️ Atenção

pandas × Polars no pandera. O backend de pandas é o mais antigo e completo. O de Polars é mais novo e tem algumas diferenças que vale conhecer: (1) você importa de pandera.polars em vez de pandera; (2) ao validar um LazyFrame, o pandera checa apenas o schema (colunas e tipos), não os valores — para validar valores, passe um DataFrame já materializado; (3) alguns recursos do backend pandas (como validações por grupo) ainda não existem no de Polars. Para o nosso objetivo — garantir o contrato de entrada do modelo — os dois resolvem igualmente bem.

Em testes:

# tests/test_schema.py
import polars as pl
import pytest
import pandera.errors as pa_errors
from src.data.schema import HousingSchema

def test_schema_aceita_dados_validos(amostra_housing):
    HousingSchema.validate(amostra_housing)   # não deve lançar

def test_schema_rejeita_latitude_impossivel(amostra_housing):
    df = amostra_housing.with_columns(pl.lit(999.0).alias("Latitude"))
    with pytest.raises(pa_errors.SchemaError):
        HousingSchema.validate(df)

Esse segundo teste é o que pega o schema drift do início do capítulo: se um dado impossível chega, ele barra antes do modelo.

pandera × Pydantic: quando usar cada um

Os dois validam dados, mas em granularidades diferentes — e não competem:

pandera a tabela inteira

Valida um DataFrame de uma vez — colunas, tipos, ranges e nulos na coluna toda, em lote. Feito para dados tabulares de ML/ETL.

Pydantic um registro

Valida um objeto/JSON por vez — campo a campo, com tipos Python. É o que usamos na borda da API (capítulo 3), a cada requisição.

São complementares: o pandera guarda a entrada do pipeline de dados (a tabela de treino/ETL); o Pydantic guarda a entrada da API (o request de inferência).

💡 Dica

Como usar pandera em produção. Coloque a validação logo no começo do pipeline — assim que os dados são carregados, antes de qualquer transformação (é o "portão"). No treino/batch, valide o dataset inteiro e falhe rápido (deixe o erro estourar). Em produção com muito volume, validar tudo a cada chamada pode ser caro: valide sempre o schema (tipos/colunas) e rode os checks de valor numa amostra dos dados que chegam, registrando/alertando sobre violações (sinal de data drift) em vez de derrubar o serviço. Use o mesmo schema nos testes e em runtime — uma única fonte de verdade do contrato de dados.

💡 Dica

pandera vs Great Expectations: pandera tem baixa curva de aprendizado, é nativo em Polars, rápido e se integra ao código de ML inline. Great Expectations é orientado a enterprise: multi-engine, governança e "Data Docs" em HTML. Para um projeto acadêmico ou um pipeline enxuto, pandera é a escolha pragmática.

Camada 3 — Smoke test: "o sistema está vivo?"

No topo da pirâmide está o smoke test. O nome vem da eletrônica: liga o aparelho e vê se sai fumaça. Não mede qualidade do modelo (acurácia, RMSE) — mede se o pipeline inteiro funciona de ponta a ponta: carrega, treina sem lançar exceção e produz output com o shape e tipo corretos.

📖 Definição

Smoke test: verificação rápida de que o sistema "está vivo" — o pipeline carrega, .fit não explode e .predict devolve algo com a forma esperada. É um teste de sanidade do sistema, não de qualidade do modelo.

Regra de ouro: use dados sintéticos mínimos, nunca o dataset real. Dados reais deixam o teste lento e frágil. O smoke test precisa rodar em milissegundos.

# tests/test_smoke.py
import numpy as np
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LinearRegression

def construir_pipeline():
    return Pipeline([("scaler", StandardScaler()), ("model", LinearRegression())])

def test_pipeline_fit_predict_smoke():
    # Arrange: dados sintéticos mínimos no shape do California Housing (8 features)
    rng = np.random.default_rng(42)
    X = rng.random((20, 8))
    y = rng.random(20)

    pipe = construir_pipeline()
    pipe.fit(X, y)              # Act: carrega e treina sem lançar
    preds = pipe.predict(X)

    assert preds.shape == (20,)        # uma predição por linha
    assert preds.dtype == np.float64
    assert np.isfinite(preds).all()    # sem NaN/inf
🔬 Exemplo

Por que esse teste vale ouro: lembra a coluna renomeada da introdução? Se o pré-processamento gerar NaN por causa de uma coluna faltante, np.isfinite(preds).all() falha imediatamente — a falha silenciosa virou um teste vermelho na sua máquina, antes do deploy.

Quantos testes são suficientes? (o caso acadêmico)

A expectativa mais citada gira em torno de 70–80% de cobertura de código. Você mede isso com pytest-cov:

pip install pytest-cov

A realidade é bem mais modesta. Um estudo de 2025 sobre sistemas de ML no GitHub (arXiv 2502.17378) encontrou que apenas 33% dos sistemas de ML têm pelo menos um teste unitário, e a mediana de funções de ML cobertas é de 5,6%.

⚠️ Atenção

100% de cobertura ≠ corretude. Cobertura mede quais linhas executaram durante os testes, não se você verificou as coisas certas. Um teste pode executar uma função inteira e não fazer nenhum assert relevante. Persiga bons asserts, não o número 100.

Para um projeto acadêmico:

  • Não persiga 100%. Cubra as funções críticas: transformers, funções de feature engineering e validações de schema.
  • Uma suíte típica de projeto acadêmico tem entre 15 e 40 testes.
  • Priorize a base (unit) porque ela é aditiva e estável.

Indo além — testes comportamentais verificam o comportamento do modelo, não só o código. São três tipos:

MFTMinimum Functionality Test

Um caso fácil que o modelo tem que acertar.

INVInvariance

Uma perturbação que não deveria mudar a predição (ex.: trocar um sinônimo).

DIRDirectional

Perturbação com efeito esperado (ex.: ↑idade → ↑probabilidade de churn).

🎯

Não são obrigatórios num projeto inicial, mas pegam bugs que cobertura nenhuma revela — porque olham para o comportamento, não para as linhas executadas.
