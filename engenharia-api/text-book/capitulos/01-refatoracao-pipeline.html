Do Notebook à Produção: Refatoração & Pipeline

Transformar código exploratório de notebook em módulos src/ limpos, aplicando SOLID, e encapsular o pré-processamento num Pipeline scikit-learn reprodutível.

"Qualquer tolo escreve código que um computador entende. Bons programadores escrevem código que humanos entendem." — Martin Fowler

Introdução

Se você é cientista de dados, provavelmente sua vida intelectual acontece dentro de um notebook. É lá que você carrega os dados, plota histogramas, testa três versões de uma feature, treina um modelo, descobre que ele é ruim, treina outro, e — eventualmente — chega a algo que funciona. O notebook é uma ferramenta de exploração excelente. O problema começa quando alguém pergunta: "Ótimo, e como a gente coloca isso em produção?"

A resposta honesta, na maioria das equipes, é constrangedora: copia-se o .ipynb para um servidor, reza-se para que as células rodem na ordem certa, e cruzam-se os dedos para que o modelo treinado hoje seja igual ao de ontem. Não é.

Este capítulo trata da ponte entre esses dois mundos. Vamos pegar um caso concreto — regressão de preços de imóveis com o dataset California Housing — e levá-lo de uma célula de notebook bagunçada até módulos src/ limpos, testáveis e determinísticos. O caminho passa por quatro ferramentas:

SOLID Princípios de design

Cinco princípios de OO aplicados a ML para separar responsabilidades e desacoplar o código.

Pipeline scikit-learn

Todo o pré-processamento encapsulado num único objeto reprodutível, sem vazamento de dados.

Polars ETL

Leitura e transformação dos dados de forma rápida e econômica em memória.

.joblib Artefato

Um arquivo único e versionável que faz predict de forma determinística — sem surpresas.

📖 Definição

Refatoração (Martin Fowler, Refactoring, 2ª ed., 2018): processo de reestruturar código existente — alterando sua estrutura interna — sem mudar seu comportamento externo observável. Refatorar não é reescrever nem adicionar features: é melhorar o design de um código que já funciona. A regra de ouro: depois de refatorar, o modelo deve produzir exatamente as mesmas predições de antes.

🎯

Refatorar = mudar a estrutura sem mudar o comportamento. Mesmas predições antes e depois.

1.1 Dois mundos: notebook vs. produção

Notebook e código de produção otimizam para coisas diferentes, e é por isso que tentar usar um como o outro dá errado.

DimensãoNotebook (exploração)Produção (módulos src/)
ObjetivoDescobrir, experimentarServir, repetir, manter
Ordem de execuçãoFora de ordem, estado ocultoDeterminística, top-down
EstadoVariáveis globais mutáveisFunções/classes encapsuladas
TestesInexistentesUnitários e de integração
ReusoCopy-paste entre célulasImports
Determinismo"Funciona na minha máquina"Mesma entrada → mesma saída

O notebook acumula estado oculto: você executa a célula 12, depois volta e edita a 5, roda a 5 de novo mas esquece de re-rodar a 8, e agora a variável X_train reflete um estado que nenhuma ordem linear de execução jamais produziria. Isso é veneno para reprodutibilidade.

🎯

Notebook é para explorar; src/ é para produzir. Estado oculto é o inimigo número um da reprodutibilidade.

💡 Dica

Quando refatorar? Não refatore enquanto ainda está explorando — você só vai jogar fora o trabalho. Refatore quando o código passar do experimento para a entrega: quando alguém vai depender dele, quando precisa rodar de novo amanhã, ou quando você se pega copiando a mesma célula pela terceira vez. A regra dos três (Fowler): na terceira repetição, extraia.

O "antes": uma célula de notebook típica

Eis o tipo de célula que todos nós já escrevemos. Funciona, produz um modelo, e é um pesadelo de manter:

# Célula 7 — California Housing (versão notebook)
import pandas as pd
from sklearn.datasets import fetch_california_housing
from sklearn.linear_model import LinearRegression
from sklearn.preprocessing import StandardScaler
from sklearn.model_selection import train_test_split

d = fetch_california_housing(as_frame=True).frame

# feature engineering "na mão"
d["rooms_per_household"] = d["AveRooms"] / d["AveOccup"]
d["pop_per_household"]   = d["Population"] / d["AveOccup"]

# OPS: scaler ajustado ANTES do split → data leakage
sc = StandardScaler()
X = sc.fit_transform(d.drop(columns=["MedHouseVal"]))
y = d["MedHouseVal"].values

X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.2)  # sem random_state!

m = LinearRegression().fit(X_tr, y_tr)
print(m.score(X_te, y_te))   # score otimista e irreproduzível

Conte os problemas: (1) o StandardScaler é ajustado no dataset inteiro, antes do split — vazamento de dados; (2) train_test_split sem random_state — irreproduzível; (3) a lógica de features está solta, impossível de reusar na inferência; (4) variáveis de uma letra; (5) nada disso é testável. Vamos consertar tudo.

1.2 SOLID aplicado a Machine Learning

SOLID são cinco princípios de design orientado a objetos (Robert C. Martin). Parecem "coisa de engenheiro de software", mas cada um tem um paralelo direto e útil em ML — e o próprio scikit-learn já foi desenhado em cima deles.

S Single Responsibility

Uma classe, uma razão para mudar. Separe DataLoader · FeatureTransformer · ModelTrainer.

O Open/Closed

Aberto para extensão, fechado para modificação. Adicione um transformador ao Pipeline sem editar os passos existentes.

L Liskov Substitution

Subtipos substituíveis. Troque LinearRegression por RandomForestRegressor no mesmo Pipeline e nada quebra.

I Interface Segregation

Interfaces enxutas. A API de inferência só precisa de predict — não arraste o código de treino.

D Dependency Inversion

Dependa de abstrações. Injete o transformador via TransformerMixin, não o instancie fixo.

A seguir, cada princípio com o seu paralelo concreto em um projeto de Machine Learning.

SRP — Single Responsibility Principle

"Uma classe deve ter uma, e apenas uma, razão para mudar."

A célula acima viola o SRP de forma flagrante: ela carrega dados, cria features, escala, divide e treina — tudo num bloco. Se a fonte de dados mudar, você mexe aqui. Se a feature engineering mudar, você mexe aqui. Se o modelo mudar, você mexe aqui. São muitas razões para mudar no mesmo lugar.

A correção é separar responsabilidades em unidades coesas:

🔬 Exemplo

Em vez de um monolítico DataProcessor que "faz tudo", divida em:

  • DataLoader — sabe ler os dados (e só isso).
  • FeatureTransformer — sabe criar/transformar features (e só isso).
  • ModelTrainer — sabe treinar e avaliar (e só isso).

Cada um tem uma única razão para mudar. Trocar de Parquet para uma API afeta apenas o DataLoader.

# ❌ Uma classe que faz tudo — várias razões para mudar
class DataProcessor:
    def run(self, caminho):
        df = pl.read_csv(caminho)                 # I/O
        df = df.with_columns(...)                 # feature engineering
        model = RandomForestRegressor().fit(X, y) # treino
        return model

# ✅ Uma responsabilidade por classe
class DataLoader:       # só lê dados
    def load(self, caminho): ...

class FeatureBuilder:   # só cria features
    def transform(self, df): ...

class ModelTrainer:     # só treina e avalia
    def train(self, X, y): ...

OCP — Open/Closed Principle

"Entidades devem estar abertas para extensão, mas fechadas para modificação."

Você adiciona comportamento novo sem reescrever o que já funciona. É exatamente o que o Pipeline e o ColumnTransformer oferecem: para testar uma feature nova, você acrescenta um transformador à lista de passos — não edita os passos existentes nem o código de treino. Herdar de BaseEstimator/TransformerMixin também estende o scikit-learn sem tocar no código da biblioteca.

🎯

Feature nova? Adicione um passo ao Pipeline. O resto do código nem fica sabendo.

# Pipeline já existente
passos = [("imputer", SimpleImputer()), ("scaler", StandardScaler())]

# Estender = ACRESCENTAR um passo, sem editar os que já existem
passos.insert(1, ("attribs", CombinedAttributesAdder()))   # feature nova
pipe = Pipeline(passos)
# nenhum passo anterior foi modificado — só estendido

LSP — Liskov Substitution Principle

"Um subtipo deve poder substituir seu tipo base sem quebrar o programa."

No scikit-learn, todo estimador honra o mesmo contrato (fit/predict). Por isso você troca LinearRegression por RandomForestRegressor dentro do mesmo Pipeline e nada mais precisa mudar. O contrato vale também para o seu transformador: se ele respeita a interface (fit retorna self, transform devolve um array no shape esperado), ele é substituível em qualquer ponto onde um transformador é esperado — inclusive dentro de um GridSearchCV.

⚠️ Atenção

Quebrar o contrato quebra o LSP: um transform que às vezes devolve DataFrame e às vezes ndarray, ou um fit que não retorna self, torna seu objeto não substituível e estoura erros difíceis de rastrear no Pipeline.

def build(estimator):
    return Pipeline([("prep", preprocessor), ("model", estimator)])

build(LinearRegression())            # funciona
build(RandomForestRegressor())       # também funciona — mesmo contrato fit/predict
build(GradientBoostingRegressor())   # idem; nada mais no código precisa mudar

ISP — Interface Segregation Principle

"Nenhum cliente deve ser forçado a depender de métodos que não usa."

Prefira interfaces pequenas e específicas a uma que "faz tudo". Em ML isso aparece na fronteira treino × inferência: treinar precisa de dados, validação e bibliotecas pesadas; servir precisa apenas de predict sobre um artefato já treinado. Manter essas responsabilidades separadas faz a API de inferência depender só do necessário — sem arrastar o código (e as dependências) de treino para dentro do servidor de produção.

# Treino precisa de tudo: dados, validação, bibliotecas pesadas
def treinar(): ...                       # usa polars, sklearn, etc.

# Inferência só precisa de predict sobre o artefato já pronto
class Preditor:
    def __init__(self, model):
        self.model = model
    def predict(self, X):
        return self.model.predict(X)
# a API importa apenas o Preditor — não arrasta o módulo de treino

DIP — Dependency Inversion Principle

"Dependa de abstrações, não de implementações concretas."

Em vez de o ModelTrainer instanciar internamente um StandardScaler fixo, injete o transformador como dependência. A abstração que o scikit-learn nos dá para isso é a interface TransformerMixin (tudo que tem fit/transform). Assim o treinador funciona com qualquer transformador que respeite o contrato — StandardScaler, RobustScaler, ou seu transformador custom.

# DIP: o treinador recebe o pré-processador, não o cria
class ModelTrainer:
    def __init__(self, preprocessor, estimator):
        self.preprocessor = preprocessor   # abstração injetada
        self.estimator = estimator

    def build(self):
        from sklearn.pipeline import Pipeline
        return Pipeline([("prep", self.preprocessor),
                         ("model", self.estimator)])

Isso torna o código testável (você injeta um mock), flexível (troca de implementação sem editar o treinador) e desacoplado.

src/data/io.py — carregar com Polars, salvar com joblib

Tudo que toca o "mundo externo" — ler os dados, gravar e recarregar o modelo — fica isolado num único módulo. Assim, se a fonte de dados mudar (de um dataset embutido para um arquivo ou uma API), só este arquivo é afetado: é o princípio da responsabilidade única na prática. joblib é a biblioteca padrão para salvar objetos do scikit-learn em disco — ela guarda o pipeline inteiro, já treinado, num único arquivo .joblib.

# src/data/io.py
import joblib
import polars as pl
from sklearn.datasets import fetch_california_housing
from src.config import MODELS_DIR


def load_california() -> pl.DataFrame:
    """Carrega o dataset como Polars DataFrame (eager)."""
    bunch = fetch_california_housing(as_frame=True)
    return pl.from_pandas(bunch.frame)


def save_pipeline(pipeline, name: str = "model.joblib") -> None:
    MODELS_DIR.mkdir(parents=True, exist_ok=True)
    joblib.dump(pipeline, MODELS_DIR / name)


def load_pipeline(name: str = "model.joblib"):
    return joblib.load(MODELS_DIR / name)

src/modeling/preprocessing.py — escrevendo um transformador próprio

No notebook, a engenharia de atributos ficava solta no meio das células: criávamos colunas novas com operações diretas no DataFrame. O problema é que essa mesma lógica precisa ser aplicada exatamente igual em dois momentos — quando treinamos o modelo e quando ele entra em produção para fazer previsões. Se ela vive solta, é fácil aplicar de um jeito no treino e de outro no serviço — uma das maiores fontes de erro silencioso em ML.

🎯

Lógica de feature solta no notebook = risco de aplicar diferente no treino e no serviço. Empacotada num transformador, ela viaja junto com o modelo e é aplicada igual em todo lugar.

A solução do scikit-learn é empacotar essa lógica num transformador: um objeto que segue um contrato simples — tem um método fit (que aprende dos dados o que precisar) e um método transform (que aplica a transformação). Uma vez nesse formato, o transformador "viaja junto" dentro do pipeline e é aplicado de forma idêntica em qualquer contexto.

O nosso transformador vai criar atributos derivados: razões entre colunas que costumam ter mais poder preditivo do que os valores brutos. No California Housing, em vez de usar só o total de cômodos, faz mais sentido olhar cômodos por domicílio (AveRooms / AveOccup) e pessoas por domicílio. É um exemplo clássico de feature engineering para esse dataset. Em vez de calcular isso "na mão" numa célula, transformamos em uma peça reutilizável:

# src/modeling/preprocessing.py
import numpy as np
from sklearn.base import BaseEstimator, TransformerMixin


class CombinedAttributesAdder(BaseEstimator, TransformerMixin):
    """Adiciona atributos derivados (razões entre colunas) ao California Housing."""
    AVE_ROOMS, AVE_BEDRMS, POPULATION, AVE_OCCUP = 2, 3, 4, 5

    def __init__(self, add_bedrooms_per_room: bool = True):
        self.add_bedrooms_per_room = add_bedrooms_per_room  # sem transformar nada aqui

    def fit(self, X, y=None):
        return self                                   # nada a aprender → self

    def transform(self, X):
        X = np.asarray(X, dtype=float)                # nunca alterar o array de entrada
        rooms_per_household = X[:, self.AVE_ROOMS] / X[:, self.AVE_OCCUP]
        pop_per_household = X[:, self.POPULATION] / X[:, self.AVE_OCCUP]
        new = [rooms_per_household, pop_per_household]
        if self.add_bedrooms_per_room:
            bedrooms_per_room = X[:, self.AVE_BEDRMS] / X[:, self.AVE_ROOMS]
            new.append(bedrooms_per_room)
        return np.c_[X, *new]

Cada decisão desse código tem um motivo. Vale destrinchar:

Por que herdar de BaseEstimator e TransformerMixin?

São duas classes-base do scikit-learn. TransformerMixin entrega de graça o método fit_transform (que faz fit e transform de uma vez). BaseEstimator entrega get_params/set_params, usados na busca de hiperparâmetros e para clonar o objeto. Herdando das duas, o nosso transformador é tratado pelo sklearn exatamente como qualquer outro.

Por que fit só retorna self?

Aqui não há nada a "aprender": a conta é fixa (divisões entre colunas). Mesmo assim somos obrigados a implementar o fit e a devolver o próprio objeto (self) — é esse contrato que permite encadear fit().transform(). Um transformador que aprendesse algo (uma média, por exemplo) guardaria esse valor aqui dentro.

Por que índices de coluna como constantes?

O transform recebe um array NumPy, que não tem nomes de coluna — só posições. Dar nome aos índices (AVE_ROOMS = 2…) deixa o cálculo legível e evita "números mágicos" espalhados pelo código.

Por que np.asarray e não alterar a entrada?

Convertemos para array e montamos um novo array de saída com np.c_ (que junta colunas). Nunca mexemos no X que chegou: alterar a entrada "no lugar" provoca efeitos colaterais difíceis de rastrear quando o mesmo dado passa por vários passos do pipeline.

⚠️ Atenção

O cuidado com o __init__. O BaseEstimator descobre os hiperparâmetros do transformador lendo a assinatura do __init__. Por isso duas regras valem sempre: (1) use parâmetros explícitos, nunca *args/**kwargs — senão get_params() falha e, com ele, clone() e o GridSearchCV param de funcionar; (2) no __init__, apenas guarde o parâmetro como recebeu (self.add_bedrooms_per_room = add_bedrooms_per_room), sem fazer cálculo ou transformação — toda lógica fica no fit e no transform.

💡 Dica

Transformações simples e sem estado (que não precisam aprender nada no fit) podem dispensar a classe e usar diretamente FunctionTransformer(minha_funcao). Só evite passar uma função anônima (lambda): o joblib não consegue salvar uma lambda em disco, então o modelo não poderia ser persistido depois. Use sempre uma função nomeada com def.

src/modeling/pipeline.py — montando tudo com ColumnTransformer

# src/modeling/pipeline.py
from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler

from src.config import NUMERIC_FEATURES
from src.modeling.preprocessing import CombinedAttributesAdder


def build_preprocessor() -> ColumnTransformer:
    numeric_pipeline = Pipeline([
        ("imputer", SimpleImputer(strategy="median")),
        ("attribs", CombinedAttributesAdder()),
        ("scaler", StandardScaler()),
    ])
    return ColumnTransformer(
        transformers=[("num", numeric_pipeline, NUMERIC_FEATURES)],
        remainder="drop",
        verbose_feature_names_out=False,        # nomes limpos: "MedInc", não "num__MedInc"
    )


def build_pipeline(estimator) -> Pipeline:
    return Pipeline([
        ("preprocessor", build_preprocessor()),
        ("model", estimator),
    ])

Esse código monta o pré-processamento inteiro como objetos do scikit-learn. Duas estruturas fazem o trabalho:

Pipeline

Encadeia uma sequência de passos no formato (nome, transformador) — a saída de um passo vira a entrada do seguinte. Tratar tudo como um único objeto garante que pré-processamento e modelo andem sempre juntos.

ColumnTransformer

Aplica transformadores diferentes a grupos de colunas diferentes, no formato (nome, transformador, colunas). Aqui há um ramo só (tudo numérico); é essa estrutura que, amanhã, deixa tratar números e categorias em paralelo.

📖 Definição

O que é aquela tupla ("imputer", SimpleImputer(strategy="median"))? Cada passo é um par (nome, transformador). O nome ("imputer") é apenas um rótulo — serve para referenciar o passo depois (por exemplo, ao buscar hiperparâmetros: "imputer__strategy"). O transformador (SimpleImputer(strategy="median")) é o objeto que faz o trabalho — tem fit/transform, como vimos. No ColumnTransformer a tupla tem três partes — (nome, transformador, colunas) — porque ali você também diz a quais colunas aquele transformador se aplica (no caso, NUMERIC_FEATURES, a lista com as 8 features).

Lendo o ramo numérico de cima para baixo — lembrando que cada passo recebe a saída do anterior:

1 SimpleImputer(strategy="median")

Preenche valores faltantes (NaN) de cada coluna com a mediana daquela coluna — calculada no fit, só com os dados de treino. Usa-se a mediana, não a média, por ser robusta a outliers. Sem este passo, as contas seguintes quebrariam ao encontrar um NaN.

2 CombinedAttributesAdder()

Nosso transformador próprio: cria as features derivadas (cômodos por domicílio etc.) a partir das colunas já imputadas. É a feature engineering que estava solta no notebook, agora encapsulada e reaplicável de forma idêntica em treino e inferência.

3 StandardScaler()

Padroniza cada coluna para média 0 e desvio-padrão 1 (subtrai a média e divide pelo desvio, ambos aprendidos no fit). Coloca todas as features na mesma escala — essencial para modelos lineares, sensíveis à magnitude dos valores.

Por fim, build_pipeline dá o passo final: junta esse pré-processador a um estimador (o modelo) num único Pipeline — o fluxo completo vira preprocessor → model, pronto para fit e predict.

Os dois parâmetros do ColumnTransformer também são decisões conscientes: remainder="drop" descarta qualquer coluna que não tenha sido listada (em vez de deixá-la passar crua, sem tratamento), e verbose_feature_names_out=False mantém os nomes das colunas limpos na saída (MedInc em vez de num__MedInc).

💡 Dica

Por que montar o pipeline dentro de funções (build_preprocessor, build_pipeline)? Cada chamada devolve um pipeline novo e ainda não treinado. Isso evita reaproveitar sem querer um objeto já ajustado entre experimentos, deixa o código fácil de testar e permite injetar qualquer estimador: build_pipeline(LinearRegression()) hoje, build_pipeline(RandomForestRegressor()) amanhã, sem tocar no resto. É a inversão de dependência (DIP) que vimos no SOLID, aplicada na prática.

# src/modeling/train.py
import numpy as np
from sklearn.linear_model import LinearRegression
from sklearn.metrics import root_mean_squared_error
from sklearn.model_selection import train_test_split

from src.config import SEED, TARGET
from src.data.io import load_california, save_pipeline

def train():
    np.random.seed(SEED)                       # freeze seeds
    df = load_california()

    X = df.drop(TARGET)                         # Polars DataFrame
    y = df[TARGET].to_numpy()

    X_train, X_test, y_train, y_test = train_test_split(
        X.to_pandas(), y, test_size=0.2, random_state=SEED   # determinístico
    )

    save_pipeline(pipeline)
    return pipeline

1.5 Reprodutibilidade e o fim do data leakage

Como o Pipeline previne data leakage

📖 Definição

Data leakage é quando informação de fora do conjunto de treino (tipicamente, do conjunto de teste) "vaza" para o processo de treinamento, inflando artificialmente a performance medida. A forma mais comum: ajustar (fit) um scaler, imputador ou seletor de features no dataset inteiro, antes do split treino/teste.

O mecanismo do Pipeline é elegante e elimina a classe inteira de erro:

  • pipeline.fit(X_train, y_train) chama fit_transform em cada step exceto o último, e fit no estimador final. Os parâmetros (média/desvio do scaler, mediana do imputador) são aprendidos apenas com X_train.
  • pipeline.predict(X_test) chama apenas transform nos steps de pré-processamento e predict no estimador. O teste nunca influencia os parâmetros.

Em validação cruzada, o Pipeline faz isso automaticamente em cada fold. A documentação do scikit-learn (Common Pitfalls) ilustra com dados puramente aleatórios: pré-processar antes do split produz um R² falso de ~0,76; feito corretamente dentro do pipeline, cai para ~0,50 — o valor honesto para ruído.

⚠️ Atenção

O leakage não é um erro acadêmico raro. O paper de Kapoor & Narayanan (Patterns, Cell Press, 2023) catalogou vazamento de dados em 294 artigos científicos de 17 áreas distintas. É uma das principais causas de resultados de ML que não se reproduzem. Encapsular o pré-processamento num Pipeline é a defesa estrutural mais barata contra isso.

Reprodutibilidade: sementes, serialização e fronteiras

Sementes (random_state). Passar um inteiro (random_state=42) torna a operação determinística: mesma entrada, mesma saída, sempre. Passar uma instância de np.random.RandomState faz o estado avançar a cada uso — robusto para CV, mas não reprodutível entre execuções. Para produção, prefira o inteiro e adote o padrão "freeze seeds": um SEED = 42 central, propagado a todo componente estocástico.

Serialização. joblib.dump(pipeline, ...) persiste o objeto inteiro — incluindo todos os parâmetros aprendidos e transformadores já ajustados. Na inferência, joblib.load + .predict, e nada mais.

💡 Dica

Serialize com metadados. Salve junto do artefato um pequeno manifesto: versão do scikit-learn (sklearn.__version__), a SEED, e um fingerprint dos dados de treino (ex.: hash do arquivo). Isso permite detectar incompatibilidades de versão e auditar com o que o modelo foi treinado.

Polars na fronteira do scikit-learn

Usamos Polars (colunar, baseado em Apache Arrow) para o ETL — leitura tipicamente ~5x mais rápida que pandas e menor consumo de memória, especialmente em modo lazy (pl.scan_csv().collect()). Mas o scikit-learn não consome um LazyFrame diretamente. Duas estratégias:

  1. Converter na fronteira. Faça EDA/ETL em Polars e, ao entregar ao scikit-learn, df.to_numpy() (zero-copy quando numérico e sem nulos). Um LazyFrame precisa de .collect() antes.
  2. Saída Polars do scikit-learn (≥ 1.4). Desde o scikit-learn 1.4 (jan/2024): preprocessor.set_output(transform="polars"), ou globalmente set_config(transform_output="polars").
import polars as pl
from sklearn import set_config

set_config(transform_output="polars")   # todos os transformadores devolvem Polars
# ...ou por objeto:
preprocessor.set_output(transform="polars")
⚠️ Atenção

Armadilhas na fronteira: (1) LazyFrame não passa direto — colete antes; (2) OneHotEncoder usa sparse_output (não mais sparse, desde sklearn 1.2); (3) verbose_feature_names_out=True gera nomes como num__MedInc — use False; (4) nunca altere o X recebido dentro de um transformador — sempre produza um array novo.
