APIs de Inferência com FastAPI

Expor o modelo como uma API REST profissional, com validação de contrato (Pydantic), observabilidade (logging + latência), endpoints de saúde, e entender os padrões de serving (batch, online, micro-batching, streaming).

Introdução: o modelo precisa sair do notebook

Você treinou um bom modelo. O pipeline.joblib está salvo, o RMSE está aceitável, e no notebook a célula model.predict(X) devolve previsões em milissegundos. O problema é que ninguém — nem outro time, nem um aplicativo, nem um sistema de cobrança — consegue chamar o seu notebook. Um notebook é um ambiente de exploração, não um serviço. Para que o modelo gere valor, ele precisa ser exposto: alguém faz uma pergunta ("quanto vale este imóvel com estas características?") e recebe uma resposta padronizada, validada e rápida.

A forma padrão de fazer isso na indústria é uma API REST de inferência. Neste capítulo, transformamos o modelo de regressão do California Housing — que recebe 8 features de um imóvel e prevê o preço — em uma API profissional com FastAPI. O caminho até lá tem cinco etapas:

HTTP Vocabulário REST

Recursos, verbos e status codes — a linguagem que cliente e servidor usam para se entender.

Pydantic V2 Contrato de entrada

Validar automaticamente o que entra na API, devolvendo erros claros quando o dado é inválido.

Endpoints /predict e /health

As rotas que servem a previsão e que reportam se o serviço está de pé e pronto.

Observabilidade Logging + latência

Logging estruturado em JSON e um middleware de latência para enxergar o que acontece em produção.

Serving Padrões de arquitetura

Batch, online, micro-batching e streaming — para escolher a arquitetura certa para cada caso.

O que é uma API REST

REST é um estilo de arquitetura para comunicação entre sistemas pela web. A ideia central é organizar tudo em torno de recursos — substantivos identificados por uma URL — e manipular esses recursos com um conjunto pequeno e padronizado de verbos HTTP. Na nossa API, /predict e /health são recursos.

📖 Definição

Recurso: uma "coisa" que a API expõe, endereçada por um caminho (path). /predict representa a operação de prever um preço; /health representa o estado de saúde do serviço. Verbo HTTP: a ação que você quer executar sobre o recurso (GET, POST, etc.).

Verbos HTTP

Cada verbo comunica a intenção da operação. Cinco cobrem quase tudo:

VerboUso típicoIdempotente?
GETLer um recurso, sem alterar nada (ex.: /health)Sim
POSTCriar algo novo ou disparar um processamento (ex.: /predict)Não
PUTSubstituir um recurso inteiro por uma nova versãoSim
PATCHAlterar apenas parte de um recursoNão necessariamente
DELETERemover um recursoSim
📖 Definição

Idempotente quer dizer que repetir a mesma requisição várias vezes tem o mesmo efeito que fazê-la uma única vez. GET /health dez vezes não muda nada no servidor. Já POST /predict dez vezes pode gerar dez registros (ou dez cobranças). Isso importa para retries: o cliente pode repetir com segurança uma chamada idempotente que falhou, mas precisa de cuidado com as não idempotentes.

POST, PUT e PATCH costumam confundir, porque os três "enviam dados" no corpo da requisição. A diferença está na intenção:

POSTcriar / processar

Cria um recurso novo ou dispara um processamento. Não idempotente: repetir gera um novo resultado a cada vez. É o que usamos para enviar features e pedir uma previsão.

PUTsubstituir

Troca um recurso inteiro por uma nova versão. Idempotente: enviar o mesmo objeto duas vezes deixa o servidor no mesmo estado. Ex.: substituir o cadastro completo de um imóvel.

PATCHatualizar parte

Altera só um pedaço de um recurso, deixando o resto intacto. Nem sempre idempotente — depende do que o patch faz (veja abaixo). Ex.: corrigir só o campo "preço" de um imóvel.

🔬 Exemplo

Por que o PATCH não é garantidamente idempotente? Idempotente = repetir N vezes tem o mesmo efeito que fazer 1 vez. No PATCH, depende de como a alteração é descrita:

  • Absoluto (define um valor): PATCH {"preço": 100} → repetir mantém 100. É idempotente.
  • Relativo (descreve uma mudança): PATCH "aumentar o preço em 10" ou "adicionar um item à lista" → cada repetição muda o estado de novo (110, 120…). Não é idempotente.

Como o PATCH permite o caso relativo, não dá para garantir idempotência — por isso a tabela diz "não necessariamente". O PUT, por sempre substituir o recurso inteiro, é idempotente por construção. Na prática isso importa para retries: repetir um PATCH que falhou pode aplicar a mudança duas vezes.

Para inferência, usamos POST em /predict: enviamos um JSON com as features e pedimos um processamento. Já /health é um GET: apenas lemos um estado, sem alterar nada.

Status codes

Cada resposta HTTP carrega um status code — um número de três dígitos que resume o que aconteceu. O primeiro dígito define a classe:

2xx · Sucesso

Deu certo. O 200 OK é o mais comum — a requisição foi atendida e a resposta vem no corpo.

4xx · Erro do cliente

A requisição tem algo errado (dado inválido, rota inexistente, sem permissão). Quem precisa corrigir é quem chamou.

5xx · Erro do servidor

A requisição estava ok, mas algo quebrou no servidor. O problema é nosso, não do cliente.

(Existem ainda 1xx informativo e 3xx redirecionamento, raros numa API de inferência.) Os que mais aparecem no nosso caso — clique para ver quando cada um ocorre:

Accordion · Referência rápida de status codes HTTP
Requisição bem-sucedida. /predict retornou a previsão; /health confirmou que está tudo certo.
Recurso criado. Raro em inferência síncrona; aparece quando um job de predição em batch é registrado/agendado.
Requisição malformada (JSON inválido, sintaxe quebrada). Também usado para erros de negócio que você decide sinalizar manualmente.
Rota inexistente (ex.: cliente chamou /predction).
Sintaxe OK, mas o dado é inválido. O FastAPI/Pydantic retorna isto automaticamente quando a validação falha (ex.: HouseAge: "trinta").
Cliente excedeu o rate limit.
Erro inesperado no servidor (ex.: exceção dentro de model.predict).
Serviço indisponível — típico quando o modelo ainda não carregou ou a instância está sobrecarregada.
⚠️ Atenção

422 (Pydantic, automático) vs. 400 (erro de negócio). Um equívoco comum é tratar tudo como 400. O 422 é gerado automaticamente pelo Pydantic quando o tipo/range do dado é inválido — você não escreve código para isso. O 400 é para erros que você decide sinalizar (regra de negócio violada).

FastAPI: o essencial

FastAPI é um framework web em Python construído sobre Starlette (camada web/ASGI) e Pydantic (validação de dados). Três características o tornam ideal para servir modelos:

Docs automáticas
OpenAPI / Swagger

A partir dos seus tipos e modelos Pydantic, o FastAPI gera, com zero configuração, uma interface interativa em /docs (Swagger UI) e outra em /redoc. Quem for consumir a API consegue testá-la pelo navegador.

async / await
Concorrência

Rotas podem ser assíncronas, permitindo alta concorrência em operações de I/O sem travar o processo.

Injeção de dependência
Depends()

Você declara o que uma rota precisa e o FastAPI fornece — e essas dependências também aparecem no Swagger.

🎯

Carregue o modelo uma única vez no startup, nunca por request. Recarregar a cada chamada custa CPU e memória e abre brechas para race conditions.

💡 Dica

A forma moderna e correta é usar o lifespan com @asynccontextmanager: o código antes do yield roda no startup (carrega o modelo), o código depois roda no shutdown.

⚠️ Atenção

@app.on_event("startup") está DEPRECADO. Use lifespan. E cuidado: se você definir on_event e lifespan juntos, o on_event é ignorado silenciosamente.

Estrutura da aplicação

from contextlib import asynccontextmanager
from fastapi import FastAPI
import joblib

ml_models = {}

@asynccontextmanager
async def lifespan(app: FastAPI):
    # STARTUP: carrega o pipeline treinado uma única vez
    ml_models["housing"] = joblib.load("pipeline.joblib")
    yield
    # SHUTDOWN: libera recursos
    ml_models.clear()

app = FastAPI(title="California Housing API", version="1.0.0", lifespan=lifespan)
⚠️ Atenção

Segurança — joblib.load executa código. Desserializar um .joblib/pickle roda código arbitrário embutido no arquivo. Só carregue artefatos que o seu próprio pipeline gerou (confiáveis). Nunca carregue um .joblib recebido de fonte desconhecida. Para dados simples, prefira JSON.

Validação de contrato com Pydantic

O contrato da API é a definição exata do que entra e do que sai. Pydantic é a biblioteca que o FastAPI usa para isso: você descreve o contrato como uma classe Python, e cada requisição é validada automaticamente contra ela.

O fluxo, quando um POST chega, é:

  1. o FastAPI lê o JSON do corpo da requisição;
  2. tenta encaixá-lo na sua classe, convertendo tipos quando faz sentido (a string "41" vira o número 41.0);
  3. confere as restrições que você declarou (faixas de valor, formatos);
  4. se algo não bate, devolve 422 automaticamente com a lista de erros — você não escreve nenhuma linha de validação;
  5. se tudo bate, sua função recebe um objeto Python já validado e tipado.
📖 Definição

BaseModel é a classe-base de todo modelo Pydantic — herdar dela é o que liga a validação automática. Field(...) descreve um campo: o ... (reticências) o marca como obrigatório; os argumentos seguintes declaram as restrições (gt=0 = maior que zero; ge/le = maior-ou-igual / menor-ou-igual) e a description que aparece na documentação do Swagger.

⚠️ Atenção

Use Pydantic V2 (jun/2023). Material antigo usa V1 e vai te confundir. Principais mudanças: @validator → @field_validator (exige @classmethod); classe interna Config → model_config = ConfigDict(...); validadores cross-field: @model_validator(mode="after"); mode="before" valida antes da coerção de tipo, mode="after", depois.

Modelo de entrada e saída

As 8 features do California Housing são MedInc, HouseAge, AveRooms, AveBedrms, Population, AveOccup, Latitude e Longitude.

from pydantic import BaseModel, Field, ConfigDict, field_validator

class HousingFeatures(BaseModel):
    model_config = ConfigDict(extra="forbid")  # rejeita campos desconhecidos

    MedInc:     float = Field(..., gt=0,   description="Renda mediana do bloco (10k USD)")
    HouseAge:   float = Field(..., ge=0,   le=100)
    AveRooms:   float = Field(..., gt=0)
    AveBedrms:  float = Field(..., gt=0)
    Population: float = Field(..., gt=0)
    AveOccup:   float = Field(..., gt=0)
    Latitude:   float = Field(..., ge=32.0, le=42.0)
    Longitude:  float = Field(..., ge=-125.0, le=-114.0)

    # Field já cobre tipo e range (gt, ge, le...). O @field_validator entra
    # quando a regra NÃO cabe numa restrição — aqui, normalizar a entrada:
    @field_validator("MedInc", "AveRooms", "AveBedrms", mode="before")
    @classmethod
    def aceitar_virgula_decimal(cls, v):
        # roda ANTES da conversão de tipo: aceita "8,32" (vírgula) além de 8.32
        if isinstance(v, str):
            return v.replace(",", ".")
        return v


class PredictionOut(BaseModel):
    predicted_price: float = Field(..., description="Preço previsto (100k USD)")

Duas coisas a notar. O @field_validator serve para o que o Field não consegue: tipos e faixas de valor (gt, ge, le…) já são responsabilidade do Field — repetir isso num validador seria redundante. O validador entra quando a regra exige lógica: normalizar/limpar a entrada (como acima, com mode="before", que roda antes da conversão de tipo) ou validar algo que uma restrição não expressa. E o PredictionOut declara o contrato de saída: usado como response_model na rota, ele faz o FastAPI validar e documentar também a resposta, não só a entrada.

💡 Dica

Field oferece muito mais que ge/le: gt, lt, min_length, max_length, pattern (regex), multiple_of, max_digits, decimal_places. Para checagens que envolvem mais de um campo (ex.: "AveBedrms não pode ser maior que AveRooms"), use @model_validator(mode="after"), que recebe a instância já validada.

Os endpoints /predict e /health

/predict

Aqui aparece uma decisão de arquitetura importante. É tentador montar a matriz de features e chamar o modelo dentro da própria rota — mas misturar lógica de ML com a camada web é má prática: fica difícil de testar (você precisaria subir a API inteira só para checar uma previsão) e difícil de reusar (um job em batch não aproveita uma lógica presa numa rota HTTP).

O padrão é separar em camadas: a rota cuida do HTTP (receber, validar, responder) e um serviço cuida da regra de ML (preparar as features e prever). Começamos por uma função que converte o objeto validado no formato que o pipeline espera:

# api/service.py — lógica de ML, sem nada de HTTP
import pandas as pd

FEATURE_ORDER = ["MedInc", "HouseAge", "AveRooms", "AveBedrms",
                 "Population", "AveOccup", "Latitude", "Longitude"]

def to_features(data: HousingFeatures) -> pd.DataFrame:
    """DataFrame de 1 linha com colunas NOMEADAS — o contrato do pipeline.

    Por que não um array cru? O ColumnTransformer seleciona as colunas
    POR NOME; um array sem nomes seria rejeitado na inferência.
    """
    return pd.DataFrame({nome: [getattr(data, nome)] for nome in FEATURE_ORDER})

def predict_price(model, data: HousingFeatures) -> float:
    return float(model.predict(to_features(data))[0])

A rota fica enxuta — só orquestra o HTTP e delega a previsão ao serviço:

# api/app.py — camada web
from fastapi import HTTPException
from housing.api.service import predict_price

@app.post("/predict", response_model=PredictionOut)
async def predict(features: HousingFeatures):
    model = ml_models.get("housing")
    if model is None:
        raise HTTPException(status_code=503, detail="Modelo indisponível")
    try:
        preco = predict_price(model, features)
        return PredictionOut(predicted_price=preco)
    except Exception as exc:
        raise HTTPException(status_code=500, detail=f"Erro na inferência: {exc}")
🎯

Com a previsão numa função pura (predict_price), você a testa sem subir a API e a reaproveita fora dela — num job em batch, num notebook, num teste. A rota vira só uma "casca" HTTP.

/health

Um health check é um endpoint simples que responde a uma pergunta: "estou de pé e pronto para atender?". Ele não é chamado por usuários, e sim pela infraestrutura:

  • o balanceador de carga decide se manda tráfego para esta instância;
  • o orquestrador (ex.: Kubernetes) decide se reinicia o contêiner quando ele trava;
  • ferramentas de monitoramento acompanham o uptime e disparam alertas.

Como é chamado o tempo todo, deve ser barato e rápido — nada de rodar uma predição de verdade. Mas precisa checar o que realmente importa: no nosso caso, se o modelo foi carregado.

⚠️ Atenção

/health que sempre retorna "ok" é inútil. Se ele não checa se o modelo carregou, ele mente: o orquestrador acha que está tudo bem enquanto a API devolve 503 em toda predição.

@app.get("/health")
async def health():
    loaded = "housing" in ml_models
    return {"status": "ok" if loaded else "degraded", "model_loaded": loaded}
💡 Dica

Em Kubernetes, separe /live e /ready. O liveness (/live) responde se o processo está vivo (reinicia o pod se travar). O readiness (/ready) deve falhar enquanto o modelo não carregou, evitando que o tráfego seja roteado para uma instância que ainda não consegue prever.

Observabilidade: logging estruturado e latência

Em produção, "imprimir na tela" não basta. Você precisa medir (quanto tempo cada request leva) e registrar de forma pesquisável (o que aconteceu).

Middleware de latência

Um middleware é um código que envolve toda request: roda antes de a rota ser chamada e depois de ela responder. É o lugar perfeito para cronometrar a latência e anexar o resultado a um header.

import time
from fastapi import Request

@app.middleware("http")
async def add_process_time_header(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    elapsed = time.perf_counter() - start
    response.headers["X-Process-Time"] = str(elapsed)
    return response
💡 Dica

Use time.perf_counter(), não time.time(), para medir durações. O perf_counter é um relógio monotônico de alta resolução, mais preciso para intervalos curtos e imune a ajustes do relógio do sistema.

⚠️ Atenção

Ordem dos middlewares importa. O último middleware adicionado é o mais externo e executa primeiro na entrada (e por último na saída). Pense na cebola: a request atravessa as camadas de fora para dentro e a resposta volta de dentro para fora.

Logging estruturado

Por que estruturado (em JSON)? Porque texto plano é difícil de pesquisar em escala. Ferramentas de observabilidade — Elasticsearch, Datadog, Loki, CloudWatch — consomem JSON nativamente, então você filtra por campos (latência, status, id do usuário) sem inventar expressões regulares frágeis.

O logging embutido do Python funciona, mas é cerimonioso de configurar (handlers, formatters, níveis). Uma opção mais simples e muito popular é o loguru: um único objeto logger pronto para usar, com saída em JSON ligada por um parâmetro.

import sys
from loguru import logger

# serialize=True emite cada log como uma linha JSON, pronta para ingestão
logger.remove()                                  # remove o handler padrão
logger.add(sys.stdout, serialize=True, level="INFO")

# uso dentro da rota — bind() anexa campos extras ao log:
logger.bind(rota="/predict", latency_ms=12.3).info("predicao concluida")

O que o bind(...) faz? Sozinho, logger.info("predicao concluida") registra só a mensagem. O bind(campo=valor, ...) devolve um logger com esses campos extras anexados — e, com serialize=True, cada um vira uma chave no JSON de saída. É isso que torna o log pesquisável: em vez de caçar texto, você filtra por rota = "/predict" ou latency_ms > 100.

Além disso, bind devolve um logger reutilizável: você "carimba" um valor uma vez — por exemplo, um id da requisição — e reusa, para que todas as linhas daquela requisição saiam com o mesmo campo:

log = logger.bind(request_id=req_id)     # carimba o id uma vez
log.info("validando entrada")            # sai com request_id
log.info("predicao concluida")           # sai com o MESMO request_id

# cada chamada acima vira uma linha JSON parecida com:
# {"message": "predicao concluida", "level": "INFO",
#  "request_id": "a1b2c3", "rota": "/predict", "latency_ms": 12.3}

Em produção, costuma-se registrar pelo menos rota, status, latência e um identificador de correlação (o request_id). É ele que permite juntar todos os logs de uma mesma requisição — mesmo quando ela passa por vários serviços.

💡 Dica

Exclua /health do log de acesso. O orquestrador o chama de segundo em segundo; deixá-lo no log enche os registros de ruído e esconde o que importa.

Padrões de serving: escolhendo a arquitetura

Nem todo modelo precisa de uma API que responde na hora. A forma de servir as predições — o padrão de serving — depende de dois números e do que o problema exige. Antes de tudo, dois conceitos:

Latência

O tempo entre a pergunta e a resposta — por exemplo, 50 ms para uma previsão. É o que o usuário sente enquanto espera; quanto menor, melhor a experiência.

Throughput (vazão)

Quantas previsões o sistema entrega por unidade de tempo — por exemplo, 5.000 por segundo. É a capacidade total; importa quando o volume é grande.

🎯

Os dois puxam para lados opostos: juntar requisições e processá-las em grupo aumenta o throughput (usa melhor o hardware) mas piora a latência de cada uma (todas esperam o grupo encher). O requisito de latência — quanto o usuário pode esperar — é o que decide o padrão. Ele costuma ser escrito como um SLO, por exemplo: "99% das respostas em menos de 200 ms".

Os quatro padrões

batchoffline, em lote

As previsões são calculadas antes, em lote (ex.: toda madrugada), e guardadas para consulta. Latência alta (minutos a horas), throughput enorme, custo baixo. Quando: o resultado pode esperar — relatórios, segmentação mensal de clientes.

onlinetempo real

Uma requisição → uma previsão na hora. Latência baixa (ms), serviço sempre ligado, custo mais alto. Quando: o usuário espera a resposta — fraude, recomendação, chatbot. É o padrão deste capítulo.

micro-batchingonline em pequenos lotes

Variante do online: junta as requisições que chegam numa janela curta (ex.: 50 ms) e processa o lote de uma vez. Troca um pouco de latência por melhor uso da GPU. Quando: alto volume em tempo real.

streamingfluxo contínuo

Reage a um fluxo de eventos que nunca para (via Kafka/Flink), processando cada um à medida que chega. Quando: os dados chegam continuamente — sensores (IoT), cliques, logs.

💡 Dica

Online × micro-batching × streaming, em uma frase cada: o online responde a perguntas isoladas, uma de cada vez, quando alguém pergunta; o micro-batching é online que agrupa por eficiência; o streaming não espera ninguém perguntar — reage a um fluxo que chega sozinho, sem parar.

Como decidir, na prática

Parta sempre do requisito de latência:

  • O usuário está esperando a resposta (P99 abaixo de ~200 ms): use online — e, sob alto volume, micro-batching para aproveitar melhor a GPU.
  • O resultado pode ser consumido depois: use batch — mais simples e barato, sem precisar de um servidor sempre ligado.
  • Os eventos chegam continuamente e precisam ser tratados na hora: use streaming.

O que muda na infraestrutura

Um detalhe importante: nem todo padrão de serving é uma API. A arquitetura — e as ferramentas — mudam bastante de um para o outro:

🎯

Só o online (e o micro-batching) são uma API de fato. O batch é um job agendado que grava previsões; o streaming é um consumidor de eventos. São serviços de naturezas diferentes.

PadrãoÉ uma API?Como serveInfra / ferramentas típicas
BatchNãoUm job roda o modelo sobre o lote e grava as previsões; quem precisa apenas consulta o resultado prontoAgendador (cron, Airflow, Prefect) + armazenamento (banco, data warehouse, S3)
OnlineSimAPI sempre ligada que responde a cada requisição na horaFastAPI + servidor ASGI (uvicorn/gunicorn), atrás de um balanceador, com réplicas em containers (Docker/Kubernetes)
Micro-batchingSim (API + buffer)API que agrupa requisições numa janela curta antes de chamar o modeloServidor de inferência especializado (BentoML, NVIDIA Triton), geralmente com GPU
StreamingNãoConsome um fluxo contínuo de eventos e publica os resultados em outro destinoBroker de eventos (Kafka, Pulsar) + processador de stream (Flink, Spark Streaming)

Por isso a pergunta "qual padrão de serving?" vem antes de escrever a API: ela define se você vai construir um serviço HTTP, agendar um job ou subir um consumidor de eventos. Neste capítulo focamos no online — o caso mais comum para servir um modelo sob demanda.
